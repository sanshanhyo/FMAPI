# FMAPI 全域数据发现任务图谱

> **当前交付是所有目标领域的待办清单，不是开始采集，也不是现有成果汇总。** 面向未来 FA 和外部 mod 所需读取的数据，先把要找什么、如何分派、怎样验收列清楚；SDK 与写入/控制接口不在本轮范围。
>
> 适用研究目标：Windows FM27 原生游戏数据。下面是可持续扩充的目标地图，并不承诺穷尽所有内部字段，也不保证每个目标存在、已加载或可读取。P0/P1/P2 决定先后，不从总范围删除长期任务。

## 二、优先级与任务粒度

- **P0**：先形成 FA 当前经理/俱乐部的可用只读数据闭环。
- **P1**：覆盖日常管理与外部 mod 常用领域。
- **P2**：全世界、长历史、实时细粒度或复杂语义，保留在总图谱内。
- 每个任务 ID 是独立可分派的“找入口 → 列字段 → 解码 → 对照 → 交付数据”单元，不代表一次扫描或一天能完成。无法获取的目标仍交付阻塞与已排除路径。
- 以下任务都指**读取**状态、规则、选项或记录，不授权执行对应游戏操作。比如转会任务读取报价，训练任务读取计划，消息任务读取回复选项，不发送报价、不改训练、不回复消息。

## 四、每个任务的固定输出和验收

每个任务 ID 都必须交付，而不只是每个大领域交一段介绍：

- `<ID>/inventory.csv`：目标拆成字段；逐项填写未开始/候选/已观察/已验证/阻塞/不可用，包含 raw、类型、语义、单位、关系、来源与版本。
- `<ID>/findings.md`：入口、定位/解码方法、复用代码、已排除路径和未解决问题。
- `<ID>/sample.sanitized.json`：最小脱敏结构化样例，包含 capture 和实体引用；无数据时写明原因，不伪造样例成功。
- `<ID>/validation.md`：UI/已知事实对照及边界样本；同状态重复读取和重载后的结果分别记录。
- `<ID>/handoff.md`：完成了什么、哪些仍未知、共享入口、下一批最小采集请求与所需权限/环境。

**统一验收**：目标范围逐项有结论；采到的数据可追溯、可关联、单位明确；未知保持未知；无数据的任务有具体阻塞/已尝试路径；一次成功不得标成跨版本稳定。整合者按领域内任务和字段的真实分母报告覆盖，不以“任务已派出”计完成。

领域额外验收：身份验证当前经理而非页面人物；名册对账完整性；属性对照缩放；金额对照币种/周期；赛事关联具体赛季；实时数据说明采样频率与丢失事件；正文逐字对照而非相似度；历史注明年份覆盖；规则区分定义与计算结果；隐藏属性不能只凭数值范围命名。

## 五、六个调度组，不是六个领域上限

六组是方便用户派给模型的调度方式；任一组可以继续按 ID 拆给多个模型。共享现场采集必须串行/限流，离线分析和各自代码可并行。

- **A 世界与组织**：ENV、IDX、MGR、CLB、STF、BRD、FAC。先交 UID 与组织入口，后续任务不必等全组结束。
- **B 人员与培养**：PLY、PST、TRA、MED、YTH、NAT。先交人员/可用性，再扩属性、训练医疗与发展。
- **C 合同与招募**：CON、FIN、TRN、SCT。先交合同与金额语义，再扩市场/球探/历史。
- **D 赛事与比赛**：FIX、CMP、MAT、LIVE、REG、HIS。先赛程与赛后记录，再实时/规则/历史。
- **E 战术与阵容**：TAC，协作 B 的位置/状态、D 的比赛状态。阵型、角色、指令、定位球分别拆包。
- **F 消息与文本**：MSG、LOC；整合负责人另持 INT 与公共目录。先准确元数据，再完整正文与模板覆盖。

```text
G0 回收已有研究 + ENV/LOC 最低规范
  → IDX / MGR / CLB 最低 UID 和实体入口
    → PLY/STF → CON/FIN/TRN/SCT
    → PLY → PST/MED/TRA/YTH/NAT
    → FIX/CMP/REG → MAT/LIVE/HIS
    → PLY + TAC → 阵容/角色/指令
    → MGR + LOC + IDX → MSG
上述各域 → INT 跨域验收
共享设施/地理/董事会/世界/历史任务在依赖入口可用后持续并行
```

任务之间共享实体引用不意味着必须等待全部发现完成。没有现场数据的 worker 先做已有代码回收、字段拆解与最小采集请求；所有新扫描须另由用户安排的执行阶段开始。本次仅整理清单。

以下是未来执行时的细化协议。它不缩减上面的完整目标地图；其中 Later 等同于总图谱中的 P2。现有成果仅用于避免重复研究，不能替代待办任务。

# 附录 A：先取得数据，再建设 SDK

> 适用范围：Windows FM27、原生游戏进程的只读数据研究。目标是尽快交付可验证、可关联、可重复读取的数据，使 FA 能回答实际问题。本阶段不实现 SDK，不写游戏内存，不自动推进比赛、日期或处理消息。
>
> 本文是待发现范围与验收计划，不是“全部字段已存在或可读取”的承诺。游戏版本、加载联赛、界面状态和存档规模都会影响可用数据。清单允许新增，未找到的字段必须显式保留为未知。

## 1. 先冻结事实，避免重复逆向

本节依据截至 2026-11-03 已核研究记录整理，尚未完成逐项源码审计；以下证据不代表每项已经集成至远端 FMAPI。

- 仓库：https://github.com/sanshanhyo/FMAPI 。现有 SDK/Core 是 mock 骨架，不能描述为已实现的原生 SDK。
- Windows 本地分支 `research/alawell-message-reader` 存在尚未推送的提交 `10a5724`、`d1f5177`、`99aba1d`。这些本地研究提交尚未同步至远端 FMAPI；必须先由能访问该电脑的执行者导出经检查的源码、字段笔记和测试结果，再合并或推送到独立研究分支。不能假设云端模型能直接读取本机游戏进程。
- 本地已提交、尚未推送的研究中，当前实例的 `GameCurrentManager/GCuM` 指针与 `humanmanager → FULL_CONTRACT → TEAM → CLUB` 关系相符。多经理、重新载入和切换经理尚未测试，不能当成通用身份定位方案已验收。
- 本地已提交、尚未推送的成果包含 27 名 UID 球员的位置研究：门将熟练度原始值、14 个具名活动位置原始值与 natural mask；其中 2 名门将 native 值 ≥15。这里只描述已观察样本，不把阈值推断推广为所有球员和版本的规则。
- 已打包的 FA reader 已可调用相关读取能力，但 FMAPI SDK 尚未接入；它涉及日期、经理候选、俱乐部与未完整名册的 uid/name/club/team，以及 person 的 `reflexesRaw`、`handlingRaw`、`anticipationRaw`、`jumpingRaw`、`heightCm`、`dob`、合同日期与原始工资关系。字段语义、完整性及单位仍需逐项确认。
- 有赛程和战术候选研究，尚不能视为完整验证。用户确认过去的比赛插件可读取赛后统计，但精确字段清单不可得，必须先找回代码和样本再列为已实现。
- 消息模板研究仅部分成功：first/short 等内容仍未解清，没有已验证的完整准确正文读取能力。

## 2. 优先级与完成定义

- **P0：FA 可用最小闭环。** 确认“我是谁、执教哪队、有哪些球员、谁能上场、下场比赛是谁和何时、当前战术与阵容、需要注意的合同及消息”。优先当前经理和当前俱乐部，不要求全数据库遍历。P0 字段读取失败必须显示 unavailable，不能填 0、空字符串或模拟值冒充成功。
- **P1：扩大覆盖。** 预备队/青年队、更多俱乐部、赛事、属性、详细财务与转会、统计和完整消息；仍为只读研究。
- **Later：成本高或当前收益低。** 全球完整历史、所有模板与边缘赛事、隐藏机制语义、逐帧比赛数据等。是否可行由证据决定，不阻塞 P0。
- **明确延期。** SDK 公共接口设计、长期兼容性抽象、写入/控制能力、自动转会或回复消息。可以写最小研究 reader 或离线校验脚本，但不能以建设 SDK 代替数据发现。

P0 完成必须满足：最低字段集合逐项有证据、ID 可关联、单位与时间可解释、缺失原因可见、当前队伍名册数量有对照，并通过本节后述状态变化测试。若只能完成候选字段，报告“P0 未闭环”，不得以文档写完代替数据可用。

## 3. 所有工作包共同遵守的数据协议

### 字段目录

每个字段必须记录：

`domain, entity, field, priority, status, raw_type, raw_value_example, decoded_type, semantic_definition, unit, scale, currency, wage_period, nullable_reason, source_path, game_build, discovery_session, evidence_ref, validation_cases, scope, owner, next_step`

状态统一为：`not_started / candidate / observed / validated / blocked / unavailable`。

- `candidate`：仅找到可能位置或路径；`observed`：至少一个样本与界面/已知事实对应；`validated`：达到本包验收，并注明验证范围。单次观察不等于跨重载可靠。
- source_path 是可复现的对象关系/定位算法及代码版本，不只是一次会话的裸地址。裸地址只作本地临时诊断，不作实体 ID。
- raw 与 normalized 分开保存；未知枚举保留原始值。不要为迎合 UI 强行猜解码。
- 金额必须注明币种、原始缩放与显示币种是否换算。工资必须注明 weekly/monthly/yearly/unknown；周期未知时不年化、不混算。区分余额、预算、估值、价格和实际成交额。
- 日期必须区分游戏内日历、现实采集时间、合同边界日期和时间戳；日期型数据不强加时区。年龄须注明按哪一个游戏日期计算。
- 每次快照带 `capture_id, captured_at_utc, game_date, game_build, process_session_id, load_epoch, source_state, completeness`。进程重启或读档后重建指针；旧会话地址不可复用。
- 身份优先复用经验证的游戏 UID，并记录实体类型和存档/数据库作用域。无法证明跨存档稳定时，只承诺当前存档稳定。无 UID 的记录可用经验证的复合键，并标记 collision/unstable 风险。
- 关系统一给实体引用：manager→person；person→contract→team→club；team→fixture；fixture→competition/match；tactic→team/player；message→sender/recipient/related_entity。允许未知外键，不把同名人物硬关联。
- 每份数据注明完整性：全部/部分/当前页面可见/已加载对象/未知。缺失、隐藏、未加载、未解码和真实为零必须区分。

### 共用交付物

每路在自己目录 `docs/research/data/<package>/` 提交：

1. `inventory.csv`：逐字段目录，包括失败项与来源。
2. `findings.md`：入口、对象关系、定位步骤、解码与失败条件。
3. `sample.sanitized.json`：最小、脱敏、可关联的结构化样例；禁止整块内存转储。
4. `validation.md`：UI/已知结果对照、边界样本、通过与未通过项。
5. 最小研究脚本或补丁（如确有需要）、运行命令、依赖与版本。只读，不搭 SDK。
6. `handoff.md`：已完成、可复用定位、阻塞、下一批所需采集；包含字段数量和 P0 剩余项。

下列六路仅为 P0 示例批次，实际分派以上方全域调度组及任务 ID 为准。六路只改各自目录及独立脚本路径。公共目录、总目录和共享采集器由整合负责人修改，避免并发覆盖。

## 4. 六路并行工作包

### A：当前身份、俱乐部与实体关系

**P0 要读**

- [ ] 游戏日期、构建、当前会话/加载状态。
- [ ] 当前人类经理 person UID、姓名、当前团队/俱乐部 UID 与名称；标明候选经理与活动经理的区别。
- [ ] 经理→合同→团队→俱乐部关系；团队类型、所属俱乐部和一线队入口。
- [ ] 当前俱乐部一线队名册入口、名册总数及人员 UID 去重规则。

**P1 要读**：预备/青年/国家队关系，俱乐部国家与联赛，球场、设施、声望、教练和工作人员、董事会目标（若存在可验证入口）。

**Later**：全世界俱乐部与人员索引、历史任职、所有类型俱乐部关系。

**已知与起点**：复用 GCuM 与 humanmanager 关系证据；当前只验证过一个实例。不要硬编码当前经理、俱乐部或 UID。

**独立输出**：身份解析证据、实体索引、关系样例、加载失效规则。

**验收**：至少当前会话与一次独立重载的身份/UI 对照；单经理、多经理、切换经理分别记录结果。未具备多经理测试条件时明确限制，不能宣称通用当前经理识别。一线队名册计数应与同一状态界面对齐，差额逐个解释或标记未解决。

### B：球员、位置、状态与可用性

**P0 要读**

- [ ] 球员 UID、姓名、当前 team/club 引用、出生日期/年龄、身高。
- [ ] 位置熟练度原始值、自然位置判定及阈值证据；门将与其他位置均须覆盖。
- [ ] 现有 reflexes/handling/anticipation/jumping 原始字段及已确认语义，保留 raw。
- [ ] 体能、比赛锐度/状态、疲劳、士气：逐项找出真实字段、范围和更新时机，不把相似值互换。
- [ ] 伤病状态、预计回归；停赛、赛事资格/注册状态与不可用原因。须区分“没查到”和“可上场”。
- [ ] 球员与下一场赛事关联后的可用性判断；若资格未解出，只输出已知限制，不能断言可用。

**P1 要读**：技术/精神/身体/门将完整属性清单、惯用脚、角色适配、训练表现与训练计划、赛季统计、表现、发展趋势、国家队征召、租借与青年队归属。

**Later**：隐藏属性、完整成长历史、所有球员与跨联赛遍历。隐藏字段须说明并非游戏界面可见，不猜测语义。

**已知与起点**：27 名样本、14 个具名活动位置及门将原始值应先回收；不要把这 27 人当作完整球队或全部数据库。

**独立输出**：球员表、位置编码字典、availability 明细及证据链。

**验收**：覆盖门将与多个外场位置；至少健康/受伤/停赛等实际可取得状态的对照，并标明未覆盖状态。位置和属性的量纲不能只靠范围猜测。与 A 的 UID join 可复现，重复/缺员有解释；下一场可用性未知项保留 unknown。

### C：合同、财务与转会

**P0 要读**

- [ ] 球员与经理合同 UID/归属关系、合同开始/到期日期、合同状态。
- [ ] 工资 raw、币种、缩放、结算周期、球队承担比例（若可得）；无法证实时保留 unknown。
- [ ] 当前俱乐部转会预算、工资预算、已用工资；先辨认预算与余额，不以任意金额字段替代。
- [ ] 当前已存在的转会/租借/续约事项：当事人、状态与期限；没有可验证入口时列阻塞。

**P1 要读**：奖金与条款、解约金、合同选项、租借分摊、转会分期/附加条款、估值/要价、报价、转会名单、经纪人信息、球探报告、收入支出与债务。

**Later**：完整财务历史、董事会预算规则、全部转会历史与经济机制解释。

**已知与起点**：现有合同日期与 raw wage 关系可以复用，但不能推定工资周期与全部合同条款已解出。

**独立输出**：合同表、财务快照、进行中事项表、金额/周期解释。

**验收**：至少多个金额与日期的 UI 对照；不同工资显示周期/币种的测试须由采集负责人协调，不自动改设置。未获测试条件时列明范围。关联球员与俱乐部；租借、无合同、到期等边界能取则测，不能取则记待测。不得把玩家估值当作报价或可成交价格。

### D：赛程、比赛、统计与事件

**P0 要读**

- [ ] 下一场及近期赛程：fixture UID、主客队 UID、赛事/赛季、日期时间、主客场、状态。
- [ ] 最近已完赛结果、比分、球员出场、位置、分钟、评分及现有比赛插件真正能读取的统计字段。
- [ ] 可用赛事规则与停赛适用范围，为 B 的下一场可用性提供关联。
- [ ] 区分赛前/进行中/完赛记录及尚未确定时间、延期等状态。

**P1 要读**：射门、射正、控球、传球、xG 等逐项验证；进球、助攻、换人、黄红牌、伤病等事件及时间；积分榜、赛程阶段、赛季球员/球队统计、对手近期表现。

**Later**：实时球与球员坐标、逐帧轨迹、完整事件流/回放、所有赛事历史。不能把赛后摘要称为实时事件流。

**已知与起点**：优先找回用户使用过的比赛插件，列出它实际输出的字段。当前只有“曾能读取赛后统计”的用户确认，没有精确字段清单；赛程候选也需验证。

**独立输出**：fixture/match/event 表、统计字典、赛事关联与状态说明。

**验收**：至少一个待赛、一个完赛样本与 UI 对照；能获得进行中样本时另测。各统计明确按球队/球员、单场/赛季、全场/半场维度及单位。时间区分比赛分钟、补时、游戏日期；事件排序与去重规则可复现。不要为了测试自动开始或推进比赛。

### E：战术、阵型与阵容

**P0 要读**

- [ ] 当前队伍活动战术槽与选中槽的区别、战术名称/UID（如有）、阵型及位置槽。
- [ ] 首发、替补、未入选人员 UID 与位置槽关联。
- [ ] 各位置的角色和职责原始枚举及已验证解码。
- [ ] 心态、团队指令与个人指令中能稳定读取的字段；未解码项不得猜填默认值。

**P1 要读**：多个战术方案、定位球安排、对手指令、队长/主罚顺序、战术熟练度、训练与战术关联。

**Later**：完整战术语义模型、动态比赛阶段全部变化、任何自动调整或写入。

**已知与起点**：有候选入口，不代表阵型、首发和指令已完整验证。

**独立输出**：战术/槽位/阵容结构、枚举表、球员 UID 关联样例。

**验收**：阵容人数、位置与界面同状态一致；区分计划阵容和实际比赛阵容。至少两种已存在方案可访问时做对照。用户手动切换后的更新测试集中预约，不由各 worker 分别操作游戏。活动槽/页面选中槽无法分清时显式阻塞。

### F：收件箱、新闻与待处理事项

**P0 要读**

- [ ] 消息稳定标识或经测试的复合键、日期、顺序、类别、发送者、接收经理、关联俱乐部/球员/赛事。
- [ ] 标题、已读状态、是否需回复、回复期限；仅在有可靠字段时声明，不根据标题猜“必须处理”。
- [ ] 正文读取路径与模板实例参数；完整、部分、未解析分别标记。
- [ ] 用结构化已验证内容支撑 FA 的提醒；如果只有标题或片段，只呈现片段，不补写成完整原文。

**P1 要读**：first/short 等模板差异、多语言/富文本、占位符和复数、附件、链接对象、选项/截止时间的只读描述、新闻订阅与筛选。

**Later**：全部消息模板、完整历史归档、所有媒体与社交内容。自动点击选项、回复、标记已读均不在本阶段范围。

**已知与起点**：本地消息分支是首要复用材料；目前模板仅部分解析，first/short 未解决，不能发布“完整准确正文已可读”。

**独立输出**：消息记录、模板/参数目录、部分解析的明确边界、重复与归属规则。

**验收**：选取现有可访问的不同类型消息，逐字对照标题与正文；至少覆盖有参数/无参数、短/长内容、特殊字符等实际可取样本。每种模板独立计正确率和未解析数，不能用平均正确率掩盖错误正文。无法完整还原时 P0 只接受准确标题/元数据并明确正文缺口，不伪称完整消息能力。

## 5. 依赖 DAG 与最快执行顺序

```text
G0 回收已有成果 + 统一版本/采集协议
 ├─ A 身份与实体入口 ──> A 的 manager/team/club/person UID 基线
 ├─ B/C/D/E/F 的旧代码整理、离线分析、字段目录（可立即并行）
 └─ 共享采集负责人执行有预算的只读采集

A UID 基线 ──> B 球员名册与属性
A UID 基线 ──> C 合同/俱乐部财务
A UID 基线 ──> D 赛程/赛事/比赛
A UID 基线 ──> E 战术与人员槽位
A UID 基线 ──> F 收件人/发送者/关联实体
B 球员 UID + D 下一场赛事规则 ──> 下一场可用性
B 球员 UID + E 槽位 ──> 可解释的当前阵容
A/B/C/D/E/F ──> I 统一快照与跨域验收 ──> FA P0 只读数据闭环
```

执行轮次：

1. G0 回收与目录化先行；六路同时研究已有代码和脱敏样本，不同时扫进程。
2. A 先给最低身份/关联结果，其他路不必等 A 全部 P1 完成。
3. 六路分别提出最小采集请求，由同一负责人合并、去重、按状态执行。
4. 六路在同一 capture 上并行分析、写自己的最小脚本和证据；整合负责人解决公共字段冲突。
5. 先补齐 P0，再做受控的重载/经理切换/日期状态验证；其余人继续离线 P1。
6. 发布实际通过的字段清单、FA 可用样例与剩余缺口，再按收益推进 P1/Later。

## 6. 采集预算、并行边界与测试矩阵

- 只有具有该 Windows 电脑访问能力的执行者能采集本机游戏内存。其他模型负责代码阅读、样本分析、解码、测试设计和文档；不假设“云端后台进程”可以接管本机进程。
- 同一 live process 只允许一个采集负责人持有采集锁。全地址空间扫描、批量指针遍历、较大区域读取等重操作必须串行并有批准的预算，不可六路各自重复扫描。
- 每个请求填写目标、已知入口、范围、最大读取字节数/对象数、耗时上限、重试次数、预期证据。预算由采集负责人按机器与游戏状态确定；达到上限、出现卡顿/读取异常或状态漂移就停止本次采集并记录，不能无限扫描。
- 先做已有入口的小范围读取，必要时才升级发现范围。跨多个区域读取期间记录开始/结束游戏状态；发生日期、载入或阵容变化时标记 incoherent，不声称原子快照。
- 读档、切换经理、切换战术、推进日期/比赛和改设置等状态操作统一预约，并依授权由用户或指定执行者完成。六路禁止同时操作游戏；只读任务不自动获得这些操作的权限。
- 每路独立 branch/worktree；公共文件由整合者合并。禁止提交原始 dumps、密钥、令牌或游戏存档；仅提交最小脱敏样例与可复现方法。

测试矩阵至少记录：当前稳定状态、重复读取同一状态、重新载入同一存档、进程重启、不同经理/切换经理、不同俱乐部、游戏日期变化、赛前/进行中/完赛。不是每路每项都适用，但必须填 pass/fail/not_tested/not_applicable 与原因。没有测试条件时给出清晰的验证边界，不冒充通过。

## 7. 整合包 I：交付的是数据，不只是发现报告

- [ ] 汇总六路字段目录；同名字段冲突保留证据并指定唯一负责人。
- [ ] 生成同一 capture 的最小统一 JSON：context、manager、club、teams、players、availability、contracts、finances、fixtures、matches、tactics、messages；空域明确缺失原因。
- [ ] 检查 UID 去重和外键、数据类型、日期边界、金额单位、工资周期、枚举 unknown、字段刷新时间及快照一致性。
- [ ] 用数据回答：当前执教谁？一线队是否完整？下场对谁？有哪些已知不能上场的人及原因？当前阵容/战术是什么？有哪些已知合同到期/预算风险？有哪些确实需要处理的消息？
- [ ] 每个答案能回溯到字段与证据；不够回答时直接列缺口，禁止用 UI 推测或 mock 填满。
- [ ] 输出进度：P0 validated/observed/candidate/blocked 字段数，完整率的分母，覆盖存档/版本/场景；不要只报告“完成百分比”。
- [ ] 本阶段结束条件：P0 数据闭环达到已声明的验收范围，或逐项列出需要用户/本地环境才能解除的阻塞。之后的 SDK 设计另立任务。
