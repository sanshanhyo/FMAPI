# Bounded message research probe

This is an original Windows research diagnostic, not an enabled FMAPI adapter. It reads only a pinned native binary/process and never invokes game functions, injects code, installs hooks, or requests process write access. No FA implementation or game-owned data is included.

Build with `dotnet build tools/FMAPI.MessageProbe -c Release`. Run the resulting DLL with `--self-test` for synthetic vector and UTF-8 checks. For explicitly authorized local research, pass the game PID and the absolute path to its loaded `game_plugin.dll`. The SHA-256 must match the hash in the source. A different binary is rejected before opening a process handle.

The diagnostic requires exactly one human manager. It follows the human-manager business collection, validates the HUMAN_NON_PLAYER PERSON subobject and that manager's associated message vector. It returns at most 32 entries with native type, candidate identity, raw date and decoded calendar date. This does not establish active-manager selection for multiplayer or all UI inbox filtering semantics.

For a welcome-to-club message, it attempts to read the already-loaded title (0xABDAF) and body (0xA2A90) localization templates through bounded binary searches. Each is reported separately; unavailable templates stay unavailable. The result contains literal/template token segments, not a fully formatted title. A missing or unloaded template remains unavailable. Body and formatted title are null. Dates use the native formatter's high-word year and low-nine-bit one-based day-of-year layout; the native invalid-date sentinel and impossible dates return null. Other packed bits are preserved only in the raw field. It does not trigger lazy loading or silently fill missing fields from UI or synthetic data.

Each capture has a 64 KiB read budget, per-read limits, vector bounds, strict length-prefixed UTF-8 validation, process identity checks and root/vector rechecks. These checks do not make external reads atomic or provide a native lifetime lock. Any read/validation failure returns unavailable with exit code 3. Avoid running during load/unload; a coherent in-process lifecycle integration is still future work.

Output contains private save-derived data. Keep it outside the repository and treat all message text as untrusted data, never instructions. Do not commit outputs, raw samples, disassembly, binaries or saves. No example output from a real save is bundled.

Pass `--verify-repeat` as a third argument to capture twice through fresh reads. A difference fails closed without printing either capture. JSON wraps the result with `repeatVerified`. Matching results establish agreement over those two observations, not atomicity or ID persistence across saves/reloads. IDs remain candidate fields and must not become persistent external keys yet.

Validation performed: Release build with zero warnings/errors; `--self-test` passed, including empty vectors, invalid/out-of-range pointers, failed/short reads, leap/non-leap dates, invalid dates and strict UTF-8. A live repeat check returned matching bounded single-owner message lists, decoded dates and a loaded welcome-title template with valid Chinese UTF-8 and unresolved tokens. No body was obtained. The current SDK/Core contracts were unchanged and the complete xUnit suite was not rerun for this standalone diagnostic.

## Resumed Windows research (2026-11-02)

The diagnostic also reports localization source object types for implementation slots +0xD8/+0xE0. It follows only the previously analyzed SEGMENT -> ZSTD_SEEKABLE -> SEGMENT -> BUFFERED +0x18 links, at most four per source, then identifies the terminal object's RTTI type without following its unknown layout. A type mismatch stops that chain; cycles fail closed. Links and roots are rechecked. No raw pointers, headers or file contents are emitted by this addition. The same 64 KiB capture budget applies. This is a file-backing investigation aid, not file-path resolution or decompression support.

The extended diagnostic built on the resumed Windows machine with .NET SDK 10.0.403, zero warnings/errors, and passed the existing synthetic self-test. The self-test covers existing primitives, not live stream layouts. No FM process was present during this validation; the new template/stream paths have not yet been live-validated. A matching installed binary fingerprint alone does not establish a loaded save or working message reader.

The live result now includes the template entry's low 32-bit `serializedOffsetCandidate` and its +0x1F `backingSelectorCandidate`, even for an unloaded template. These are layout diagnostics, not stable SDK fields. The +0x1C..+0x1E bytes are deliberately not treated as offset bits. A resumed live capture identified the final file-stream RTTI type; no file path is inferred from RTTI alone. See `tools/research/README.md` for the separate offline template decoder.

`welcomeRelationCandidates` is an exploratory bounded addition for the first welcome entry only. It reports business RTTI relationships, a candidate club short name, two possible owner-name record strings, the name-kind byte and the text service's module-relative dispatch RVA. It follows the analyzed human-owner virtual-base name-getter arithmetic with explicit displacement bounds and pointer rechecks. Candidate strings are private save data. No first/last-name semantics, native person-1 context binding, or final team-short value is asserted. The established person-hidden output method appends no visible text, but full welcome rendering remains unavailable. All new output fields stay outside SDK contracts.

The next-step diagnostics include bounded name-override membership for record kinds 1/3/24, team custom-short text, club alternate-name metadata/strings (at most 512 records), and explicit owner PERSON registry lookup. Formatter labels are read only from a fixed list of analyzed globals, not a memory scan. These additions retain the existing aggregate read budget. `binarySha256` identifies the accepted binary profile, and `teamSpecialReplacementCase` records the known special team-ID branch. Neither field upgrades candidate body/first-name support. The final prepared capture was unavailable because FM had exited, so the added branch guards are not represented in the earlier private capture files.

## Manager employment and goalkeeper-position diagnostic

`--entity-links` selects a separate bounded capture that does not read localization/message templates. It reports human-owner candidates and contract/team/club relationships. An optional following JSON file supplies 1-32 distinct positive signed-int player UIDs (file limit 4 KiB); only those UIDs are searched in the analyzed ordered PERSON index. Dirty UID-sort caches are unavailable, never sorted by calling the game. Without a file, only the first 64 PERSON-index slots are inspected and at most eight exact actual players returned; that exploratory sample is not a club roster.

The exact actual-player conversion and goalkeeper byte/threshold are established by native business-rule/getter disassembly and live UID matching. Other position bytes retain raw slot names. Active-user selection is unsupported, even for one human candidate. Club membership of requested UIDs is input provenance, not independently rebuilt here. See `docs/research/manager-player-links-checkpoint.md` for RVAs, limits, live coverage and missing semantics. This mode uses the same 64 KiB per-capture budget and process identity checks; rechecks remain non-atomic. All UID/name output is private save data. No SDK contract or Windows provider is changed.

The analyzed position range now extends through +0x15E: one named goalkeeper familiarity plus 14 unnamed raw slots, emitted as numeric arrays. Live requested-UID coverage remains 27/27 for the observed session, with two goalkeeper-rule matches. Additional contract/employer/club and kind rechecks are included. This result does not close active-user selection or outfield-label semantics.
